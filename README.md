# Audio Notes Platform — Gnani Internship Task

A production-minded take-home implementation for the Gnani internship assessment.

## Assignment

Build a web platform where a user uploads an audio file and receives:

- a transcript generated by Gnani ASR
- an LLM-generated summary
- a history of previous uploads that can be reopened
- visible progress and failure states
- an `/architecture` page explaining the system and linking the GitHub repository

The assignment explicitly requires Next.js, FastAPI, Postgres, storage, background jobs, deployment, visible failure handling, and progress reporting.

## Recommended stack

| Layer | Choice | Reason |
|---|---|---|
| Frontend | Next.js + TypeScript | Explicit assignment requirement; good upload/polling UX |
| UI | Tailwind CSS | Fast, consistent implementation |
| Backend | FastAPI + Python | Explicit assignment requirement; strong async/API ecosystem |
| ORM / migrations | SQLAlchemy 2 + Alembic | Explicit DB models and reproducible migrations |
| Database | Managed PostgreSQL | Reliable persistent job/history state |
| Object storage | S3-compatible private bucket | Large-file uploads, presigned URLs, no frontend proxying |
| Queue | Redis | Simple durable-enough queue for the take-home architecture |
| Worker | Celery | Clear background-job model and retry controls |
| ASR | Gnani Prisma v2.5 Batch STT | Required provider and correct choice for long recordings |
| Summary LLM | Provider behind a small adapter | Keeps the summarizer replaceable |
| Deployment | Vercel frontend + managed backend/worker services | Simple public demo topology |

Use one concrete provider combination and document it. Do not change providers mid-project unless a real deployment limitation forces it.

## Important Gnani API fact

Gnani's REST STT endpoint accepts audio up to 60 seconds, so it should not be the primary path for this application. Gnani's Batch API is designed for long recordings. Batch supports files up to 4 hours per file; direct multipart uploads are limited to 10 MB per file, while cloud-storage/public HTTPS sources remove the 10 MB byte cap and remain bounded by the 4-hour duration limit. Public HTTPS URLs, including S3 presigned URLs, are supported by the Create Job API.

Official docs:
- https://docs.gnani.ai/api/STT/speech-to-text
- https://docs.gnani.ai/api/STTBatch/Introduction
- https://docs.gnani.ai/api/STTBatch/Create_Job

## Processing model

The HTTP request should never wait for transcription or summarization.

Synchronous:
1. Validate request metadata.
2. Create a DB record.
3. Generate an object-storage upload URL.
4. Return the upload instructions.
5. Confirm upload completion.

Background:
1. Validate object exists and metadata is consistent.
2. Generate a time-limited HTTPS URL for Gnani.
3. Create Gnani Batch job.
4. Start the job.
5. Poll at least every 10 seconds; use exponential backoff for transient failures.
6. Download the transcript result before the Gnani `transcript_url` expires.
7. Persist the transcript and update status.
8. Generate the summary.
9. Persist the summary and mark the task complete.

## Local development

Requires Docker, Python 3.12 and Node 20+.

```bash
cp .env.example .env                       # then fill in the Gnani and storage values
docker compose up -d --wait                # Postgres + Redis on 127.0.0.1

python -m venv .venv                       # Windows: .venv\Scripts\activate, else: source .venv/bin/activate
pip install -r backend/requirements-dev.txt
(cd backend && alembic upgrade head)

# three terminals, from the repo root:
uvicorn app.main:app --app-dir backend --reload --port 8000
celery -A worker.celery_app worker -l info   # on Windows add: -P solo (prefork is unsupported there)
(cd frontend && npm install && npm run dev)  # http://localhost:3000 shows API / Postgres / Redis status
```

Checks (all must pass):

```bash
pytest && ruff check . && ruff format --check . && mypy backend/app worker
(cd frontend && npm run lint && npm run typecheck && npm run build)
```

Use `127.0.0.1`, not `localhost`, in `DATABASE_URL` / `REDIS_URL` on Windows: `localhost` tries IPv6 first
and every connection then waits out its whole connect timeout before falling back to IPv4.

The test suite needs the Postgres container running (`docker compose up -d --wait`); it creates and migrates its
own `audio_notes_test` database. Storage is faked in tests.

## Storage setup (AWS S3)

1. Create a **private** bucket (keep "Block all public access" on).
2. Create a dedicated IAM user with this policy (replace `YOUR_BUCKET`), and put its access key in `.env`:

   ```json
   {
     "Version": "2012-10-17",
     "Statement": [
       { "Effect": "Allow", "Action": ["s3:PutObject", "s3:GetObject", "s3:DeleteObject"],
         "Resource": "arn:aws:s3:::YOUR_BUCKET/*" },
       { "Effect": "Allow", "Action": "s3:ListBucket", "Resource": "arn:aws:s3:::YOUR_BUCKET" }
     ]
   }
   ```

   `s3:ListBucket` (on the bucket ARN, **without** `/*`) is required: without it S3 answers 403 instead of 404 for a
   missing object, and `/complete` cannot tell "not uploaded yet" from "no permission".
3. Add a CORS rule on the bucket so the browser can upload directly (add the deployed frontend origin too):

   ```json
   [{ "AllowedOrigins": ["http://localhost:3000"], "AllowedMethods": ["PUT"],
      "AllowedHeaders": ["*"], "ExposeHeaders": ["ETag"], "MaxAgeSeconds": 3000 }]
   ```

## API

| Endpoint | Purpose |
|---|---|
| `POST /api/uploads/initiate` | validate, create a job, return a signed URL to PUT the file to |
| `POST /api/uploads/{id}/complete` | verify the upload landed in storage (idempotent) |
| `GET /api/uploads`, `GET /api/uploads/{id}` | history and job detail |
| `GET /api/health` | Postgres and Redis status |

Interactive docs are at `/docs` on the running API. Errors always look like `{"error": {"code", "message"}}`.

## Definition of done

The demo is done only when a fresh user can open the deployed URL and:

1. upload a normal 2+ minute audio file without the frontend waiting on a long HTTP request;
2. see upload progress;
3. see a processing state after upload;
4. reopen the page and still see the job state;
5. eventually read the transcript;
6. see a summary generated from the stored transcript;
7. refresh the page and retain the result;
8. see a useful error if upload, ASR, storage, or LLM fails;
9. open `/architecture` and understand the end-to-end flow;
10. find the GitHub repository link from `/architecture`.
